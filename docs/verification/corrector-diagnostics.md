# Bounded corrector diagnostics

This review investigates the weak locked-cohort recovery and the degradation at
zero injected fault. It does not change the experiment, select a replacement
checkpoint, or tune a correction from locked results. The formal artifacts remain
those described in [analysis reproduction](analysis-reproduction.md).

**Status:** source review, checkpoint metadata validation, and analytical probes
are complete; 149 focused synthetic CPU regression tests passed at the original
diagnostic stage. The subsequent release passed the full repository gate and
[release verification](publication-and-interchange.md). That engineering
acceptance does not resolve the remaining scientific questions below.

## What was checked

The three selected checkpoint files were rehashed against their original
completion receipts and run records before a CPU-only, `weights_only` load.
Embedded metadata hashes were checked, then compared with each bound training
provenance document and every epoch in its progress log. No model was constructed
and no new inference or training was performed for these checks.

For each seed, the selected checkpoint corresponds to the earliest minimum
calibration loss in the complete recorded epoch history. All three selected epoch
29. Epoch 30 has the same recorded calibration loss as epoch 29; the strict
improvement rule correctly retains the earlier checkpoint. The configured cosine
learning-rate multiplier reaches zero at the last epoch. This explains the final
tie under that schedule; it does not explain weak calibration recovery.

The run records, embedded configuration, and checkpoint metadata agree on the
seed, producer, config digest, cohort identity, preprocessing, and calibration
fault policy. The input is ordered red, green, blue, depth, valid; the fixed input
dimensions and normalization agree with the configured preprocessing contract.
The full training-loss trajectory is not present in `progress.jsonl`. It cannot
be reconstructed from calibration loss, and no such trajectory is claimed here.

The checkpoint loader in
[`checkpoints.py`](../../src/bevcalib/training/checkpoints.py) independently checks
provenance, creates the configured architecture, loads weights strictly, and calls
`model.eval()`. Its prediction path uses `torch.no_grad()` and checks input shape
and output finiteness. The training backend calls `model.train()` for each
training epoch and `model.eval()` for calibration. Both use the shared
preprocessing function. A new synthetic forward-hook regression directly observed eval mode and disabled
gradients while the caller had gradients enabled. A private negative control that
forced the loaded model back into training mode failed at that assertion;
the unchanged loader passed. A real-checkpoint CPU forward has not been performed
in this review.

## Units and inverse-transform checks

The target is a rigid-transform inverse, expressed as roll/pitch/yaw in degrees
and translation in metres. The loss divides prediction-minus-target by its
rotation and translation scales once. The predictor returns physical units; it
does not apply another output scaling.

Analytical probes checked both signs of each isolated rotation and translation
axis against a directly specified inverse, plus an exactly zero target. For
example, a pure x offset of +0.10 m requires x correction -0.10 m with the other
components zero. Expected values were not generated by `inverse_fault`.
Existing [dataset tests](../../tests/unit/training/test_dataset.py) also cover
the coupled rotation/translation case, where negating every component is wrong.
Existing [loss tests](../../tests/unit/training/test_loss.py) exercise the unit
normalization. Both modules passed in the focused CPU regression run.

## What the classical search does and does not establish

The [classical search](../../src/bevcalib/correctors/classical.py) starts at zero,
accepts only a strictly larger objective, and stays within fixed bounds and an
evaluation budget. A synthetic separable quadratic with a known reachable optimum
was recovered exactly in the analytical probe. That verifies this search example,
not that edge alignment uniquely identifies physical calibration.

The real objective rewards image/LiDAR edge alignment. Improving that objective
does not imply improving pose error, recovery, or BEV error. At zero injected
fault, identity already represents the calibration reference; moving away can
improve the proxy objective while worsening the calibration measurement.
This objective mismatch is a limitation, not proof of a particular failure cause
in every scene.

## Locked outcomes and interpretation

### Reading the zero-fault baseline

The zero entries in each axis sweep repeat the same baseline within a method;
they are not independent repetitions. Use `pitch:0` as a representative lookup
in [recovery.json](../evidence/nuscenes_calibration_v1/recovery.json):
`/runs/<method>/pitch:0/value`, with its adjacent `support` and interval fields.
Retain identity, classical and every learned seed when making this comparison.

In the released summaries, classical improves the mean edge proxy over identity
at zero fault while worsening pose and recovery. Inspect
`/runs/<method>/pitch:0/edge_score_px/value`, `rotation_geodesic_deg/value` and
`translation_norm_cm/value` in
[metrics.json](../evidence/nuscenes_calibration_v1/metrics.json).
This confirms disagreement between the proxy and calibration outcomes on this
cohort; it does not identify the frame-by-frame cause.

All methods have the same complete recovery support at zero fault, so missing
recovery observations do not explain that regression. This statement concerns
the recovery operator; it does not imply complete pixel or BEV support.

Identity can satisfy the recovery tolerances even with a small nonzero injected
fault. Consequently, beating classical at a larger fault does not establish an
improvement over leaving an already-in-tolerance calibration unchanged. Read the
individual conditions and paired intervals rather than reporting a winner by
averaging across the fault grid. Selecting a learned seed from these evaluation
results would violate the frozen study design.

All method/condition entries in [metrics.json](../evidence/nuscenes_calibration_v1/metrics.json)
were read for signed bias, absolute error, recovery, and their support. The
diagnostic inventory includes all extrinsic conditions for identity, classical,
and each learned seed. Identity-only timing controls were kept separate; they
are not missing learned runs. Null measurements and support exclusions are
retained rather than replaced by zero.

The zero-fault reference shows degradation for each learned seed and for
classical relative to identity. Learned mean rotation error exceeds the recovery
rotation threshold for each seed, while mean translation error alone is below
the translation threshold. These are aggregate means, not a count of which
criterion failed on each frame. Recovery requires both conditions per valid
frame, so those means cannot be used to reconstruct the recovery rate or prove
that rotation alone caused every failure.

The review has not identified a checkpoint swap, metadata/configuration mismatch,
or isolated-axis inverse-target error. It has not excluded all implementation
defects, established generalization, or identified the complete cause of weak
recovery. Low absolute recovery and zero-fault degradation must remain visible in
the final results, even where the learned corrector exceeds classical.

## Remaining work and rerun decision

- Focused CPU regression completed with 104 passed (exit 0): loss normalization,
  dataset inverse targets and split boundaries, engine checkpoint selection and
  provenance, and classical search. These four test modules use synthetic fixtures;
  they do not prove real-data recovery or replace backend/inference checks.
  A further 38 synthetic CPU backend, checkpoint-boundary, and inference-device
  tests passed (exit 0). The new inference-mode regression and six existing tiny
  training integration tests also passed (7 tests, exit 0). These historical
  focused checks preceded the full release gate identified above.
- No additional development-only real-checkpoint forward is scheduled: the bound
  metadata checks and synthetic loader/forward regressions address the identified
  implementation questions. A handful of finite predictions would not explain the
  observed recovery failure or establish generalization. Real-checkpoint forward
  equivalence remains untested by this diagnostic; no locked-data tuning is permitted.
- No formal training or inference rerun is justified by the checks completed so
  far. If a reproducible defect is found, record its affected producer, operator,
  methods, and conditions before deciding which outputs need replacement.
- Weak results alone do not justify changing the loss, threshold, seed, objective,
  or adding an identity fallback to this locked experiment.
